Provider adapters isolate model-provider behavior behind a stable infer response contract.

## Why adapters matter

Without an adapter boundary, the browser runtime would need to understand provider-specific output formats and error behavior directly.

Adapters keep the browser simpler by ensuring that provider output becomes a normalized `InferIntentResponse` shape.

## Current server model

The current server builds its adapter through a provider factory.

Today that mainly means:

- provider selection from config or environment
- a working `heuristic` adapter
- normalized response handling before the result leaves the server

## Current implementation truth

<Callout variant="warning" title="Current implementation">
  The current server includes a working heuristic adapter to validate the fallback architecture and response normalization flow. It proves the transport and contract, but it is not the final hosted-provider strategy.
</Callout>

## What a provider adapter is responsible for

A provider adapter should:

- accept normalized infer request input
- perform provider-specific inference work
- return a valid `InferIntentResponse`
- avoid leaking provider-specific format assumptions into the browser runtime

## What the browser still owns

Even after adapter normalization, the browser runtime still owns:

- graph grounding
- ambiguity handling
- route/context scoping
- dispatch safety

So an adapter returning a syntactically valid result does not guarantee that the browser will use it.
